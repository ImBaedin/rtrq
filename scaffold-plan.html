A monorepo shape for cross-client invalidation infrastructure.

This page describes the scaffold I would create after approval: Turbo for task orchestration, Bun for TypeScript workspaces, uv for Python packages and apps, plus room for future language SDKs, demos, docs, and shared tooling.

Primary flow REST + WebSocket
  1. 01 Server SDK invalidates a serializable query key.
  2. 02 RTRQ FastAPI server receives the invalidation over REST.
  3. 03 Server finds WebSocket clients subscribed to that key.
  4. 04 Client adapter receives the event and re-executes the query.
  5. 05 Redis later coordinates subscriptions across RTRQ server instances.

Security model

App isolation and connection rules

RTRQ should keep secrets server-side, treat browser app IDs as public identifiers, and make domain allowlists a practical browser-origin control for WebSocket subscriptions.

RTRQ app record

Created from the standalone admin UI

App ID
Public, high-entropy identifier used by browser clients and backend SDKs.
API key
Server-side secret used only by backend SDKs to authenticate invalidation requests.
Allowed origins
Optional list of browser origins allowed to open WebSocket subscriptions for that app.

Backend SDK config

{
  serverUrl: "https://rtrq.example.com",
  appId: "app_live_...",
  apiKey: "rtrq_sk_..."
}

Required for REST invalidation. The API key never appears in frontend bundles or browser config.

Frontend adapter config

{
  serverUrl: "https://rtrq.example.com",
  appId: "app_live_..."
}

Required for WebSocket subscription. Browser origin can be checked against the app allowlist.

REST invalidation

Reject requests unless the app ID exists and the API key verifies against a stored hash.

WebSocket subscription

Accept a public app ID, then enforce the app's origin allowlist when one is configured.

Admin console

Standalone servers get a local management UI for app creation, key rotation, and origin changes.

Origin allowlist

Store normalized origins such as https://app.example.com, not loose domain fragments. If no allowlist is set, the app can allow browser WebSocket connections from any origin.

Limits

Origin checks reduce browser-based interception risk, but they do not replace server-side API key authentication for invalidation writes.

Future hardening

Add rate limits, audit events, key rotation, revoked-key tracking, TLS guidance, and explicit SaaS tenant boundaries as implementation work begins.

apps/server

The self-hostable RTRQ server shell: FastAPI app, WebSocket route placeholders, REST invalidation route placeholders, standalone admin frontend, health checks, test harness, and uv project metadata.

apps/docs

Documentation site scaffold for concepts, quickstarts, SDK references, SaaS/self-hosting notes, and demo walkthroughs. Built as a TypeScript app managed by Bun and Turbo.

packages/typescript

Client core, React Query adapter, server SDK, and shared serialization/key utilities. These packages become the first production SDK family.

packages/python

FastAPI server core, Python server SDK, and a reserved Python client core package. All managed through uv workspace members.
